# S4 customer portal

Date: 2026-10-22

## Purpose

Give a customer a narrow, expiring view into the work and commercial records linked to their customer record. Board operators issue and revoke links; the customer uses the link without acquiring board or agent identity.

## Contract

- `customer_portals` stores an opaque UUID, company/customer/contact scope, a SHA-256 token hash, selected resource kinds, expiry, revocation and creator. The 256-bit random token is returned once.
- The board may explicitly allow customer-wide deliverable feedback on a grant. Contact-scoped grants cannot enable this customer-level action.
- Share URLs use `/portal/:portalId#token=:secret`. The fragment is read into page memory and immediately removed from browser history. Requests carry the secret only in `X-Paperclip-Customer-Portal`; it is absent from URL paths, query strings, request bodies and activity details.
- Public reads return allowlisted display fields only. Scope checks use the portal's company and customer on every query. Contact-scoped links only expose conversations, meetings and commitments with that exact contact association. Customer-level proposals and deliverables are omitted for contact-scoped links because the source records do not identify a contact-level audience.
- Deliverable feedback is a separate, immutable evidence record tied to the current `issue_work_products.updated_at` version and a portal-scoped HMAC reference. It records `accept` or `changes_requested` plus an optional comment and an idempotency key. It never resolves, mutates or impersonates the internal S1 review. Board operators can inspect these responses in the customer settings panel.
- Public conversation messages are recorded as inbound `contact` messages. They cannot send outbound messages or change conversation state. Comments and acceptances use portal-token-derived opaque resource references; acceptance resolves the proposal revision inside the grant's company/customer scope, then reuses `proposalService.accept` and its existing proposal bearer token internally. The proposal bearer is not returned to the portal client. Existing persisted payment URLs are displayed; this flow does not create payment links.
- Board-side creation and revocation write activity records. Public comments and proposal acceptance are audited as `customer-portal-contact`, with portal/contact references and without the token.

## Schema SQL fragment

The repository owner generates and registers the migration. The intended tables are:

```sql
CREATE TABLE customer_portals (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  company_id uuid NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
  customer_id uuid NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  contact_id uuid REFERENCES contacts(id) ON DELETE CASCADE,
  token_hash text NOT NULL,
  resource_kinds jsonb NOT NULL DEFAULT '["deliverables","proposals","meetings","conversations","commitments"]'::jsonb,
  allow_deliverable_feedback boolean NOT NULL DEFAULT false,
  expires_at timestamptz NOT NULL,
  revoked_at timestamptz,
  created_by_user_id text,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX customer_portals_token_hash_uq ON customer_portals(token_hash);
CREATE INDEX customer_portals_company_customer_idx ON customer_portals(company_id, customer_id, created_at);
CREATE TABLE customer_portal_feedback (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  company_id uuid NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
  customer_id uuid NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  portal_id uuid NOT NULL REFERENCES customer_portals(id) ON DELETE CASCADE,
  target_kind text NOT NULL DEFAULT 'work_product' CHECK (target_kind = 'work_product'),
  target_id uuid NOT NULL,
  target_version text NOT NULL,
  decision text NOT NULL CHECK (decision IN ('accept', 'changes_requested')),
  comment text NOT NULL,
  actor_kind text NOT NULL DEFAULT 'portal_token_holder' CHECK (actor_kind = 'portal_token_holder'),
  contact_id uuid REFERENCES contacts(id) ON DELETE SET NULL,
  idempotency_key uuid NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (portal_id, idempotency_key)
);
CREATE INDEX customer_portal_feedback_customer_idx ON customer_portal_feedback(company_id, customer_id, created_at);
CREATE INDEX customer_portal_feedback_portal_idx ON customer_portal_feedback(portal_id, created_at);
```

## Current limits

The portal lists deliverable metadata and summaries, but does not download or upload files. The existing customer portal integration has no client admission path into storage; exposing generic company files or attachment URLs would bypass their access controls. Deliverable review resolution remains in the board-only S1 workflow; portal feedback is separate, version-bound external evidence. Calendar events are listed but not modified. Proposal deposits can only use links that were already created by the existing proposal workflow.

The customer portal router must be mounted under `/api` on the public route stack before agent bearer authentication. The public UI route `/portal/:portalId` must be added to the app router outside board navigation. The schema export and generated migration are owned by the repository integrator.
