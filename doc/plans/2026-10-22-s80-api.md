# Public business API and webhooks

## Implemented source contracts

- `productizationPublicApiV1Routes(db)` is intended for `/api/v1` before generic actor authentication. A `pcp_public_` credential is a scoped capability only; it is stored in `board_api_keys` plus `product_public_api_keys`, and `boardAuth.findBoardApiKeyByToken` refuses that prefix so it cannot authenticate as an ambient board actor on other routes.
- The server derives company and scopes from the key row. Each request checks the key expiry/revocation, the issuer's current active company membership, and the required server-side scope. Client-supplied company IDs are not accepted by the resource endpoints.
- Read-only list/get endpoints cover customers, leads, assignments, proposals, accepted deliverable results, and conversations. Responses use explicit projections; they omit lead payloads, conversation messages, customer notes/contact data, proposal terms/scope, and deliverable evidence. Lists cap at 100 records and offset at 10,000. Each request performs two authorization queries and one company-filtered entity query; there is no per-record ACL query or N+1 lookup.
- `productizationPublicApiManagementRoutes(db)` provides signed-in company administrators with key create/list/revoke and webhook create/list/rotate/revoke. Creation requires `users:manage_permissions`. Keys expire in at most 365 days; there is a serialized cap of 50 active keys and 20 active webhook destinations per company.
- Webhook URL syntax is restricted to HTTPS, and dispatch uses the existing `eventFetch`/`postEvent` guard for DNS/IP validation, redirect rejection, bounded timeouts, and HMAC signing. Secrets are generated server-side, encrypted with the local encrypted secret provider, and revealed only on create or rotation.

## Durable event delivery

`businessWebhookEventForActivity({activityId, companyId, action, entityId, occurredAt})` is a pure helper for the root-owned activity-log integration. It returns an ID-only event for `lead.created`, `proposal.accepted`, `deliverable.accepted`, or `conversation.created`, or `null`. The event ID is the activity UUID; the payload contains only company ID and entity ID. Root should insert that result into `businessWebhookOutbox` in the activity transaction using `onConflictDoNothing`.

`businessWebhooksService(db).deliverDue()` fans out durably and attempts bounded deliveries with exponential retry. Delivery rows use a unique event/subscription key and send the stable event ID in the signed `webhook-id`, so receivers can deduplicate at-least-once delivery. After eight attempts, an invalid destination, or permanent HTTP rejection, delivery/subscription status becomes `blocked`; no message content or response body is retained. Root must schedule `deliverDue()` outside request handling.

## Integration and verification limits

The proposed SQL is in `2026-10-22-s80-api.sql` for root to consolidate into migration 0364. The DB schema module is `packages/db/src/schema/productization_public_api.ts`; root owns schema index, route index, OpenAPI, app mounts, and the outbox/activity-log hook. Mount v1 before `actorMiddleware`, management routes on the authenticated `/api` router, and run the delivery worker in the background. No route mount, OpenAPI contract, migration, live destination, build, test, or external delivery was performed in this area.

The public API is currently read-only. CRM read authorization is represented by explicit issued scopes plus fresh active company membership because V1 has no separate CRM read permission key. Source entities are already company-indexed; page cap bounds per-request result size. Delivery runs are bounded to 10 outbox events/deliveries per call and 10 concurrent outbound requests, and do not hold a database transaction over network I/O.

Public routes mounted below `/api/v1` are `GET /customers[/:id]`, `/leads[/:id]`, `/assignments[/:id]`, `/proposals[/:id]`, `/results[/:id]`, and `/conversations[/:id]`. Required scopes map one-to-one to each resource family (`customers:read`, `leads:read`, `assignments:read`, `proposals:read`, `results:read`, `conversations:read`). No write scope exists in v1.
