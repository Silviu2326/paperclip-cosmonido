# S95 CRM sync: producción con autoridad delegada y UI

Fecha: 2026-10-22. Fuente únicamente; no se ejecutaron tests, typecheck, build, servidores ni llamadas reales a proveedores.

## Ejecución autorizada

- Cada trabajo conserva `requestedByUserId`, provider, config/version, connection, lease attempt, task, cursor, operación, tipo de entidad, registro local y hash de argumentos. Antes de cada despacho el gateway vuelve a cargar trabajo/config/conexión, comprueba membresía activa y lease vigente, y exige que la herramienta exacta siga en el catálogo vivo de esa conexión.
- El principal es `system` con `delegatedPrincipalKind: "delegated_service"` y `delegatedCrmSyncJobId`. No se crea una sesión de usuario, una sesión de agente ni un heartbeat/run simulado. El `responsibleUserId` es quien inició el trabajo, así el gateway vuelve a resolver su grant actual. La conexión debe seguir activa, ser de la empresa y corresponder al provider configurado.
- El gateway comprueba el esquema remoto actual mediante `governedToolArguments`, conserva evaluación de policy, consumo de rate limit, invocation/audit y receipt del proveedor. Rechaza una policy que requiera aprobación porque no hay un ejecutor durable de aprobación CRM; el request de aprobación provisional se cancela y no se envía la acción.
- Las mutaciones quedan ligadas al registro local activo y a un vínculo persistido. Los creates requieren la reserva `uncertain` creada antes del despacho. No se reintenta a ciegas un create con resultado incierto. `keep_local` crea un trabajo durable de exportación focalizado; no ejecuta una llamada directa desde la ruta de resolución.
- Las configuraciones ya no incluyen nombres upstream supuestos. Cada una de las seis operaciones cliente/contacto requiere un nombre explícito y se coteja con el catálogo vivo exacto. Las respuestas HubSpot/Pipedrive siguen necesitando recibo con id antes de confirmar el vínculo.

La documentación oficial de HubSpot confirma que el conjunto de herramientas depende de la cuenta y los permisos conectados y recomienda descubrir el catálogo tras conectar; no publica un conjunto fijo que justifique valores por defecto. Por eso la UI pide los nombres exactos del catálogo actual y el gateway vuelve a validarlos en cada llamada: [HubSpot remote MCP integration](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/integrate-with-the-remote-hubspot-mcp-server).

## UI y API

- `GET /companies/:companyId/crm/sync/connections?provider=` lista conexiones coincidentes sin credenciales. La página nueva `CrmSync` permite escoger conexión, dirección, sistema principal y las seis herramientas, iniciar/reanudar trabajos y resolver conflictos o creaciones inciertas.
- El estado muestra bloqueos, vínculos, trabajos y última sincronización correcta. Caches de UI se aíslan por usuario y empresa; las solicitudes GET se descoalescen por cambio de identidad. No se muestran tokens ni secretos del proveedor.
- No hay delta de esquema SQL. Se reutiliza la lease durable de trabajos y se guarda el alcance focalizado de resolución en `cursors`.

## Cableado requerido por app

El montaje de la aplicación crea una sola instancia compartida:

```ts
const crmSyncInvoke = createCrmSyncInvoker(toolGateway);
const crmSync = crmSyncService(db, { invoke: crmSyncInvoke });
app.use("/api", crmSyncRoutes(db, { invoke: crmSyncInvoke, service: crmSync }));
// En el scheduler existente, con cadencia acotada: await crmSync.tick();
```

La UI se monta en la ruta autenticada `/crm-sync`; el enlace de navegación y mapas/OpenAPI quedan para la integración central.
