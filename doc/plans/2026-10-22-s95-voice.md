# S95 CRM callback voice execution

Status: implementation source written; no tests, build, typecheck, migration, server, or provider calls were run.

CRM callback scheduling now has an internal route into the existing Speko phone-session transport. A scheduler claims one due callback with a token and expiry, then calls `voiceSessionService.startCrmCallback(callbackId, claimToken)`. The voice service reads the destination from the current company contact record and requires it to match the phone snapshot on the approved callback. It creates an `outbound_phone` session using the distinct principal `crm_callback:<callbackId>`; this value is never built from an HTTP actor and is never treated as a company member. The voice store permits only that callback's live, fenced claim, assigned task, agent, and phone endpoint. This principal cannot pass the ordinary member authorization used by voice tools or work requests.

Immediately before `createPhoneSession`, voice asks the CRM-owned `beginDial` hook to recheck current consent, exact approval revision where required, current call autonomy, budget hard stop, contact phone, active endpoint/line, active assignee and requester, task binding, company concurrent-call limit, and per-contact daily limit. In that same fenced DB transition, `network_started_at` is set. The provider's returned session is persisted by the existing voice service. CRM marks the callback `dialed` only after it reloads that persisted session and verifies its company, callback principal, endpoint, issue, agent, outbound mode, provider session ID, and request fingerprint (which includes the server-loaded contact number).

The former HTTP `/receipt` endpoint was removed because it accepted an arbitrary session ID and could not prove that the provider session was created for that callback. Only the internal executor can record a receipt. If the process loses the response after `network_started_at`, the callback becomes `dial_unknown`; lease recovery never redials it. The next scheduler pass may reconcile an already-persisted exact provider session into a receipt. Cancellation is allowed while a dialing lease has not crossed the network-start fence. After that point the system reports that the outcome cannot be cancelled safely; this provider integration has no confirmed cancel-call operation here.

## Wiring contract for root

Construct CRM and voice services with a closure for `beginCrmCallback`:

```ts
const crmPhone = crmPhoneService(db);
const voice = voiceSessionService(db, {
  ...voiceOptions,
  beginCrmCallback: crmPhone.beginDial,
});
```

Add a bounded company scheduler tick that invokes exactly one call:

```ts
await crmPhone.processNext(workerId, voice.startCrmCallback);
```

The returned method is not an HTTP route. Root must export both CRM callback tables and add the SQL delta in `2026-10-22-s95-voice.sql` to the consolidated manual migration. The voice-session authority check also admits the new stored value; API-authenticated voice callers remain restricted to member, admin, local-board, and existing guest-intake principals.

## Schema/backfill

`crm_phone_callbacks` is a new table in this sprint's S90 source, so its required company/contact/endpoint/agent/phone/idempotency fields have no legacy rows to backfill. The S95 columns are additive nullable/defaulted fields except revision and attempt count, which safely default to 1 and 0. Existing CRM callback rows, if an environment has already applied the S90 draft fragment, receive the defaults. Legacy `dialed` rows without a persisted session carrying the exact `crm_callback:<callbackId>` principal are moved to `dial_unknown`; their prior evidence remains for audit, but they are not counted as confirmed CRM dials and are never retried. No existing voice session is relabeled as a CRM callback.
