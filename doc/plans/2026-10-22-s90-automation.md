# S3 automation handoff source work

Date: 2026-10-22

This source-only slice wires bounded commercial event production and durable handoffs for WP3, WP6, WP7, WP10, and WP13. It does not claim execution acceptance; the owning integration must mount the factory into its scheduler and apply the schema fragment.

## Implemented

- `commercialAutomation(db, deps).tick(at?)` collects bounded pages from durable CRM stage/meeting activities, inbound conversation messages, stale no-reply conversations, unattended new leads, and due commitments. Each source lane has a persisted cyclic UUID keyset cursor and a DB lease/CAS; each tick advances at most 20 rows per lane. This avoids repeatedly selecting only the newest 20 eligible rows when a lane has a larger backlog. The cursor advances only after the event handler succeeds; a failed row stays at the head for retry while other lanes can continue. The service passes events through the existing playbook service and consent check. It records per-run/per-event receipts in `crm_activities`, uses stable event keys, and relies on playbook step compare-and-set so replay and competing ticks do not dispatch the same transition twice.
- A contact reply cancels all waiting runs for that conversation. Unknown contact or channel consent fails closed. A missing channel adapter does not create an external send path.
- A board user's confirmation of a detected internal commitment changes `proposed` to `open` and creates one company-scoped assigned task for the active agent already assigned to its source conversation, with a stable idempotency key. A customer's promise creates no internal task. If the source conversation has no eligible assignee, the commitment stays confirmed and the endpoint reports the task-creation blocker; retrying safely completes the same handoff.
- Due agreement periods still create one assignment each. Renewal maintenance now creates a durable, assigned renewal-preparation task with the normal issue wakeup path and records `renewal_requested_pending_run` plus `renewal_task_id`. The task asks its actual agent run to create a proposal and open WP5 decision through existing tools, then call `POST /api/service-agreements/:id/periods/:periodId/renewal-request`. That route verifies the active heartbeat run is for the assigned issue and agent, and verifies the decision is open, belongs to that run, and names that proposal. Only then does the period become `renewal_requested` and the agreement enter `notice`. A scheduler tick does not invent `agentId`/`runId`, fabricate a proposal, claim a decision, or mark the agreement in notice as if a renewal had been requested.
- Daily brief scheduling may use an explicitly supplied authorized sender. Without one, it requires the owner to configure a same-company eligible delivery agent in their own preference; the owner’s active company membership and agent eligibility are rechecked before task creation. The supplied task adapter creates an idempotent assignment to deliver through the existing `message_send` gate. `pending_task_id` and the preferences UI show the outstanding handoff; the brief remains undelivered until a provider receipt exists. Missing agent or adapter leaves it retryable. No recipient, consent, autonomy, or provider authority is synthesized.
- `autonomyService.proposeRaise` runs as part of maintenance. It creates no decision unless its caller injects the existing WP5 callback with valid run authority; the autonomy bench gate remains unchanged.

## Mount contract

The root scheduler should instantiate `commercialAutomation(db, deps)` once beside the other long-lived services, then call `commercialAutomation.tick(now)` on its existing maintenance cadence. `deps.agreements` can supply a genuine proposal/decision callback only from a valid agent/run context. `deps.autonomy.createRaiseDecision` has the same authority requirement. `deps.dailyBrief.send` is only for an existing transport that also enforces owner-recipient authorization; otherwise the factory's assigned-task handoff is used. No changes to app/index or the heartbeat lifecycle are part of this slice.

## Schema and remaining integration

Apply the additive SQL fragment in [`2026-10-22-s90-automation.sql`](2026-10-22-s90-automation.sql) for `agreement_periods.renewal_task_id`, `daily_brief_preferences.delivery_agent_id`, `daily_brief_preferences.pending_task_id`, and the `commercial_automation_cursors` table. The schema barrel export, scheduler wiring, migration generation/execution, provider setup, and runtime proof remain owned by the integration branch. Source does not prove that the provider delivered an email/message or that an agent completed a handed-off task.
