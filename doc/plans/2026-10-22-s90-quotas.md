# S4 account quotas and billing

Production admission uses one account-scoped reservation service for company grants, all current tool-connection creators (including AI connections), outbound messages, and media video minutes. New AI connections reserve before persistence; an existing login-session result and reconnect do not consume another slot. Admission locks the commercial account, evaluates current capacity or the UTC calendar-month meter, and includes active `reserved` and `uncertain` operations. The idempotency key and request fingerprint prevent duplicate admission and key reuse for a different operation. A provider acknowledgement commits usage; a definitive pre-side-effect rollback releases it; ambiguous outcomes remain reserved as `uncertain` and are never silently refunded.

Message reconciliation settles the same stable message reservation: confirmed queued/sent/delivered/read states commit idempotently, a confirmed failed/no-effect outcome releases through the reconciliation-only settlement method, and an unresolved provider result remains uncertain. This explicit method may settle a duplicate reservation because reconciliation supplies authoritative evidence; ordinary rollback still cannot release a shared duplicate reservation. Settlement occurs before updating the local delivery state, so a quota database failure does not falsely record a reconciled message. Repeated calls return the already-settled reservation and do not add another usage event.

Company, non-terminated agent, and tool-connection capacity is read from current database rows. Jobs, messages and video minutes use durable usage events/meters. Video duration is taken from the probed input media; stop-motion duration is the configured frame count multiplied by frame duration. If a bound plan has a finite video-minute entitlement and reliable duration cannot be determined, the job fails closed before provider work. Null video-minute limits remain unmetered. Unbound/self-hosted companies retain their existing unmetered behavior. Existing spend budgets, provider gates, consent checks and approval controls remain independent.

Committed usage writes account-scoped threshold notices at 80% and 100%, deduplicated by account, metric, period and threshold. If usage jumps directly to 100%, both threshold notices are inserted. Capacity notices use the stable `current_capacity` period key; usage notices use their UTC calendar-month meter period. The product-account snapshot exposes recent notices to the account UI.

Billing status is confirmed by a current Stripe subscription lookup and matching account/customer/plan metadata. The account UI exposes current period, cancellation state and invoice links only after confirmation. Plan management, cancellation and payment updates use the standard Stripe Customer Portal. Checkout uses only configured plan price IDs; this work adds no prices and issues no remote billing calls except through the existing explicit billing request flows.

The reservation API returns an existing active idempotency row to a duplicate caller. A duplicate caller can confirm commit/uncertainty, but cannot release the shared reservation; rollback authority remains with the original owner or later reconciliation. This is safe for the current message path because the external-action gate serializes sends, and for new AI connection creation because each creation gets a UUID and a durable connection row. A generic future caller must still keep duplicate-key admission coupled to its own side-effect fence: the account lock serializes quota rows but does not itself fence the external operation.

The SQL file records the new notice table DDL for review; the consolidated 0365 migration and journal are prepared manually and were not applied. No snapshot was fabricated. No tests, build, typecheck, migration execution, server, install, or provider calls were run by this workstream.
