# S95 signup, pricing, trial and billing continuation

This slice adds a plan selection and trial continuation for signed-in account users. `Pricing.tsx` reads enabled plans from the existing public catalog and shows configured limits and whether checkout/trial are configured. It never displays a fabricated amount. The CTA preserves the selected `planId` through `/signup` and `/billing`.

The new `s95SignupRoutes(db)` exposes:

- `POST /api/productization/signup/plan` with `{ "planId": "..." }`: prepares an inactive commercial account and owner membership, with an audit event. Repeated submissions for the same user and plan reuse that account; no entitlement is granted.
- `POST /api/productization/signup/trial` with `{ "accountId": "..." }`: starts a durable trial only on a prepared account owned by the requesting user, and only after a fresh `auth_users.email_verified` check. Trial duration comes from `PAPERCLIP_PRODUCT_TRIAL_DAYS` (integer 1–365); missing/invalid configuration disables trial. The transaction locks the user and account rows, and a partial unique index allows at most one trial per account owner.

The existing `/productization/plans` response now adds `trialAvailable` and `trialDays`. Existing plan `stripePriceId` remains the sole checkout price source. Existing checkout and billing portal endpoints remain user initiated and provider calls are not made by the new signup continuation. An expired trial is denied by the existing plan gate and changed to `inactive` on the next gate evaluation.

The root integration must mount `s95SignupRoutes(db)` under the API router, register `/pricing` and `/signup`, and expose the two signup endpoints in OpenAPI. The signup page initializes in create-account mode on `/signup` and keeps the caller's sanitized `next` path. A plan continuation with no account prepares it idempotently on `/billing`; a user can explicitly start the trial there. Add the SQL in `2026-10-22-s95-signup.sql` to the consolidated migration/journal; do not run this fragment independently.

Identity email and Google OAuth are opt-in. Set `PAPERCLIP_AUTH_EMAIL_PROVIDER=resend`, `RESEND_API_KEY`, and `PAPERCLIP_AUTH_EMAIL_FROM` to configure the identity-mail transport. It sends only to Better Auth's target address through the fixed `https://api.resend.com/emails` endpoint, with a 10-second timeout, a token-hash idempotency key, and sanitized failures. Set `PAPERCLIP_AUTH_REQUIRE_EMAIL_VERIFICATION=true` to require verified email for email/password sign-in and signup; this explicit setting causes startup to fail if the complete sender config is absent, avoiding an unusable verification gate. Default self-hosted signup and sign-in remain unchanged when the setting is absent. Better Auth's built-in verification endpoint powers the resend control; callback and continuation URL are derived from the sanitized application path. The existing AgentMail business channel is not used for identity.

Set both `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` to enable Better Auth's Google provider. Partial configuration fails at startup; the secret stays server-side, and the provider requires Google's verified email claim. Register the callback URL `/api/auth/callback/google` at the externally configured Paperclip origin. `GET /api/auth/provider-availability` exposes only booleans so the UI shows resend and Google controls only when their server configuration is active. No provider credentials were set and no live email or OAuth call was made. The integration follows [Better Auth email verification](https://www.better-auth.com/docs/concepts/email), [Better Auth Google OAuth](https://www.better-auth.com/docs/authentication/google), and [Resend idempotency guidance](https://resend.com/changelog/idempotency-keys); external provider setup and live proof remain deployment tasks.

Source-only handoff: no test, typecheck, build, generated migration, server, or provider call was run in this slice. Root coordinates the narrow final checks after integration.
