# Google Calendar invoker: authority blocker and source audit

Date: 2026-10-22

## Decision

No production invoker was added. The existing calendar service deliberately defaults to `UNWIRED_INVOKER`, and the current call shape does not carry enough authority to invoke a connected tool safely. Keeping calendar reads and writes blocked is safer than borrowing a test agent or manufacturing a run context.

## Authority findings

- `googleCalendarService(db)` receives an injected `CalendarConnectorInvoker`, but `CalendarConnectorCall` has only `companyId`, `connectionId`, `toolName`, and `arguments`. The default invoker always throws an actionable 422.
- `bookingService.book` resolves anonymous bookings to the booking type's configured `hostAgentId` or `hostUserId`, then applies `gateExternalAction`. Authenticated booking, reschedule and cancel use the caller actor. The gate correctly leaves agent actions as draft, approval, or direct according to autonomy; a connector invocation still has to preserve the same actor and any owning-user connection grant.
- `toolGateway.executeTestCall` is not a suitable invoker: it requires a chosen agent and user, then creates a literal `test-call` session with no run or issue. Selecting any company agent for public booking would invent authority and bypass the real host/session relationship.
- The runtime's `createAssignedMcpTools` path is the safe existing pattern for agent tool calls: it invokes `executeTool` with the actual gateway public ID and run-scoped bearer session, and reauthorizes against the current gateway on every call. That bearer/session is not present in calendar routes or the `ExternalActionActor` used by booking.
- No provider was contacted, and no `executeTestCall` or live calendar operation was invoked.

## Narrow configuration hardening made in this source pass

- `POST /companies/:companyId/calendar/booking-types` is now board-only. Agents retain the ability to use configured booking types but cannot publish a public booking endpoint or choose its host/connection.
- Type creation validates an agent host against the same company, a user host against an active company membership, and rejects two simultaneous hosts.
- A selected connection must have an active grant matching the selected host (or an active organization grant). This verifies configured ownership without pretending that the missing runtime invocation authority exists.
- Calendar provider calls remain explicitly unavailable through the default 422 invoker. These checks only secure configuration; they do not make calendar booking live.

## Contract required before wiring

The invoker needs a server-derived, discriminated authority instead of caller-supplied agent IDs or tokens. At minimum it must distinguish:

1. An authenticated board actor with the exact user identity and the connection owner/grant to use.
2. An authenticated agent run with company, agent, run, task/issue and actual gateway-session identity, preserving current tool policy, audit and approval handling.
3. A public booking resolved to the exact active booking type and its configured host. If the host is an agent but there is no valid run/session, public execution must stay pending/rejected until the owning action dispatcher supplies one; do not manufacture a session.

The bearer token, gateway public ID, connection owner and host must be resolved from trusted server state, never from public request fields. Tool grants and connection status must be rechecked at execution time. Reschedule/cancel must follow the persisted event's connection and the authenticated caller's policy. The root integrator should own any new Tool Gateway context API if it crosses into `tool-gateway.ts` or runtime session creation.

## Source-level S1–S3 coverage review

This is a manual source review only, not runtime or acceptance proof. The source tree has substantive domain services, routes, schemas and UI for the principal workflows rather than empty contracts. From source coverage alone, the implementation appears to exceed 80% of the planned product surface; this is not an acceptance percentage and says nothing about successful production journeys. - **S1 delivery/review:** `server/src/services/deliverable-reviews.ts` and `server/src/routes/deliverable-reviews.ts` implement pending submissions, board resolution and goal/issue/company listing. `outcomeMetricsService` and `packages/shared/src/productization/outcome-metrics.ts` derive delivery, correction and acceptance metrics from canonical rows. Portal feedback is persisted as separate external evidence and cannot resolve the internal review. Root-owned migration/schema export, route/UI registration and a review journey remain unverified.
- **S2 CRM and communications:** `server/src/services/crm/{customers,contacts,opportunities,commitments}.ts`, `server/src/services/conversations/*`, their routes, and `server/src/services/external-action-gate.ts` provide source-backed workflows. Lead forms have publish/archive lifecycle and a bounded public intake route. Calendar (`server/src/services/calendar/{booking,google-calendar,slots}.ts`) has local slot rules, board-configured booking types, idempotency and an external-action gate; no default provider invoker exists, so provider availability/booking/reschedule/cancel remain blocked.
- **S3 proposals and delivery:** `server/src/services/proposals.ts` and `server/src/routes/proposals.ts` implement revision and send/accept lifecycle; Stripe webhook/payment-link code, CRM handoff and commitment services are present. Their root-owned route/page/schema/migration exports are not evidence of runtime completion until integrated.
