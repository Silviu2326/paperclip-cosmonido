# S3 WP4 autonomy bench: implementation boundary

## Current behavior

The bench service refuses to start unless both candidate replay and judge adapters are injected. The refusal happens before the `autonomy_bench_runs` insert and returns `autonomy_bench_evaluator_unconfigured`; no fixture or reference answer is used as a candidate. The evaluator also rejects `heuristic-v1` as a judge. The autonomy promotion gate independently requires a completed run, a non-heuristic judge, at least 20 evaluated cases, a passing score and the configured minimum threshold. Those checks remain unchanged.

## Why a real replay adapter cannot be supplied safely here

Heartbeat is the only current path that assembles the runtime an agent actually uses. It combines the agent adapter and effective configuration, managed AI connection binding, instruction bundle and skill versions, project/task context, connection instructions, installed tools, and—in native Runner cases—a workspace, permissions and external tool authority. Runtime selection may also resolve a provider/model fallback. Replaying a closed conversation by starting a normal heartbeat would therefore create a new run, not a read-only historical replay, and could execute tool actions or mutate current task state.

The two existing provider helpers do not provide that replay boundary. `runFastResponseProvider` hard-codes the platform's acknowledgement system prompt and is not an agent candidate. `runDecisionProvider` is a structured judge provider with a restricted configured provider/model set; it cannot reproduce arbitrary agent adapters. `prepareManagedAiRuntime` is execution preparation, not a read-only provider call: it selects runtime credentials, may refresh subscription credentials, and creates a temporary provider home. Reusing these pieces as if they replayed the full agent would silently substitute a different prompt/runtime bundle.

The current source also has no execution adapter that turns semantic tool calls into dry-run proposals while guaranteeing that every tool operation has no external or database effect. A native replay must not expose live permissions to historical inputs. Existing business gates, approvals and budget reservation cannot be replaced by a model prompt or a “do not execute” instruction.

## Missing acceptance boundary

WP4 can be completed without weakening the current gate once the server has an explicit replay harness that:

1. Pins and records the target agent's effective adapter, model/provider, instruction revision, skills/runtime configuration and tool catalog provenance.
2. Reconstructs each pre-response snapshot without exposing the reference answer to the candidate; the candidate's only action surface is a dry-run proposal interface with no provider, database or Paperclip mutation.
3. Resolves the candidate's and judge's credentials through an authorized, company-scoped AI connection, validates grants and secret freshness, and rejects any mismatch between the effective candidate runtime and the agent being qualified.
4. Reserves and settles company/agent budget for each provider invocation, records independently attributable candidate and judge cost receipts, and supports cancellation and hard timeouts without treating an uncertain provider result as free.
5. Persists separate candidate and judge model/runtime provenance. A passing score from a simplified prompt replay or a different model/runtime must not satisfy the promotion gate.

Until that replay authority and execution boundary exist, the endpoint remains explicitly unavailable before creating a run. The missing prerequisite is a server-owned, side-effect-free native replay adapter plus its scoped budget/cancellation contract—not a user's permission to let an ordinary agent run tools on old data. No diagnosis-only or prompt-only run should be called “bench qualified.”

## Reviewed source

- `server/src/services/autonomy-bench.ts`: candidate and judge must be injected before the run row is created; the candidate callback now receives a typed reference-free transcript/action input. Judge-only evaluation still cannot qualify without the native candidate runtime.
- `server/src/routes/autonomy.ts`: the board-only company-scoped run endpoint; the root app currently constructs the bench without runtime dependencies.
- `server/src/services/autonomy.ts`: independent passing-bench and promotion gate; intentionally not changed by this workstream.
- `server/src/services/heartbeat/execution-configuration.ts`, `server/src/services/heartbeat/runtime-selection.ts`, `server/src/services/native-runtime/runtime-context.ts`: current execution configuration and tool/runtime assembly boundary.
- `server/src/services/fast-response-provider.ts`, `server/src/services/decision-model-provider.ts`, `server/src/services/ai-connection-runtime.ts`: existing helpers and their narrower purposes.

No candidate or judge provider was called. No tests, build, typecheck or server were run.
