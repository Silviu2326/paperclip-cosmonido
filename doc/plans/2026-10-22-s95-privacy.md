# S95 privacy and account lifecycle

## Company retention

`productizationSecurityRoutes(db, { fileAdapter })` is company-scoped. Reads require company access; writes require the existing `users:manage_permissions` authority. A write requires a one-use preview created by the same user, company, and exact policy input. The preview expires after ten minutes. Saving checks the policy revision under a row lock, consumes the preview, records an audit event, and creates an idempotently unique company sweep. Stale revisions, previews, or mismatched input are rejected.

The default policy is disabled. Conversation retention selects only conversations that are still `closed` and whose `updated_at` is before the fixed sweep cutoff. The worker locks and rechecks each conversation before changing content, so re-opened or recently active conversations are skipped. It replaces old message bodies with a fixed marker, clears attachment metadata and provider receipt JSON, and preserves message rows, delivery state, provider IDs, conversation links, CRM records, and all company/task history. The keyset cursor and redaction counts commit together; sweeps hold a renewable DB lease and resume after process loss. Policy edits supersede old cursors instead of widening their cutoff.

File retention is scoped to company files that were already soft-deleted before the fixed cutoff. `createCompanyFileRetentionAdapter(db, storage)` uses company-scoped `StorageService.deleteObject(companyId, objectKey)`, examines at most five file rows and five versions per file in a tick, and protects any asset referenced by cases, issues, logos, media, portal files, runner reservations, agency branding, or another company file. It leaves the soft-deleted file row as a tombstone, removes versions/assets only after every storage delete succeeds, and records the purged timestamp after that confirmation. `retention_purge_started_at` is committed first; restore rejects once that marker exists, so a partial external delete cannot make missing bytes visible again. The keyset cursor advances over protected rows and reports them separately. A storage failure leaves the file tombstone retryable and the sweep cursor unchanged. The adapter fences each file operation by sweep lease and policy revision, extends the lease before storage I/O, and rechecks ownership before final metadata commit. The worker never accepts arbitrary object keys or directly deletes filesystem paths. Root must wire the same adapter to the route and `createRetentionWorker(db, { fileAdapter })` before file retention can be enabled.

## Commercial account deletion

`POST /api/accounts/deletion` is owner-only, requires the exact confirmation phrase, and creates a 30-day cooling request. `GET /api/accounts/:accountId/deletion` reports status and `POST /api/accounts/deletion/cancel` cancels only during cooling. Afterward a durable worker leases the request and requires an injected provider callback when a Stripe customer ID is present. `createAccountDeletionStripeProvider(db)` uses the existing server-only `STRIPE_SECRET_KEY` configuration, revalidates and locks the account-to-customer binding during provider I/O, checks one bounded page of up to 100 subscriptions, blocks on active or unknown subscription statuses, then issues an idempotent customer deletion. Each Stripe call times out at ten seconds; if another page is required, the worker blocks for safe operator follow-up. It makes no network request until the worker runs. The worker then deactivates the commercial account, deletes usage events/meters/reservations/notifications in batches of up to 100 per table per tick, removes commercial company grants and account memberships in batches, and anonymizes the account label. Company rows, company memberships, company content, the global auth user, and audit events stay intact. External cleanup failures remain visible as blockers; no provider call was made by this source change.

Root should mount `productizationSecurityRoutes(db, { fileAdapter })` and schedule `createRetentionWorker(db, { fileAdapter }).tick()` plus `createAccountDeletionWorker(db, { provider: createAccountDeletionStripeProvider(db) }).tick()` from the existing maintenance composition. Keep each tick bounded and single-call; workers use row leases and re-entrant state transitions. Export `companyRetention`, `retentionPreviews`, `retentionSweeps`, `retentionEvents`, and `accountDeletions` from the db schema barrel. The additive SQL is `2026-10-22-s95-privacy.sql`; fold it into the consolidated migration/journal, never execute the fragment alone.

### Remaining limits

- The integrator wired the shared storage adapter into retention routes and the independent worker lane. Without storage configuration, file retention remains fail-closed.
- Stripe credentials, subscriptions, customer state, and deletion have not been live-verified. Without server Stripe configuration, deletion stays visibly blocked with `stripe_customer_cleanup_not_configured`.
- The commercial account row and immutable account audit history remain with a redacted label and owner foreign key. This lifecycle removes commercial access and usage records; it does not delete the user's global Paperclip identity or shared company data.
- The focused `retention-files.integration.test.ts` PostgreSQL integration suite ran after implementation and after the transaction-executor hardening: 3/3 cases passed. It covers bounded preview and company isolation, protected shared assets and restore, confirmed byte/metadata purge with tombstone, and recovery after a storage failure. The suite applied migrations only in disposable test databases. Additional integrator checks are recorded in the S95 master document; no persistent database, app server, or live provider was used.
